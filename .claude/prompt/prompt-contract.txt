## Constraints

What the code MUST and MUST NOT do.

### Pattern Conformance (MANDATORY — read before you write)

Before writing ANY new code, you MUST:

1. **Find the closest existing example.** Search the target repo for a similar file to what you're about to create. Read it end-to-end. If a Pattern Reference is listed above, start there.
2. **Match its structure exactly.** File location, naming convention, decorator/annotation usage, import ordering, error handling pattern, DTO/model shape, test structure — all of it. If the repo puts services in `src/{domain}/{domain}.service.ts`, yours goes there too. If Spring Boot controllers use `@RestController` + `@RequestMapping`, yours does too.
3. **Reuse existing utilities.** Before writing a helper, search the repo for one that already does the job. If it exists, import it. If it almost exists, extend it — do NOT duplicate it.
4. **Reuse existing types/DTOs/entities/models.** Search for existing types before creating new ones. If a DTO, interface, or model covers 80%+ of your need, extend or compose it — do NOT create a near-duplicate.
5. **No new dependencies without justification.** If you need a new npm/Maven/pip package, state why no existing dependency or stdlib solution works. Wait for approval.
6. **Search for shared modules before creating new exports.** Check `libs/`, `shared/`, `common/`, or whatever directory the target repo uses for shared code. If what you need exists there, import it. If it nearly exists, extend it.

### Code Quality Gates

- MUST: KISS — simplest solution that fully satisfies the requirement
- MUST: plan first, ask questions when requirements are unclear
- MUST NOT: leave `TODO`, `FIXME`, or stub implementations in delivered code
- MUST NOT: use weak types — no `any` (TypeScript), no raw `Object`/`Map` (Java), no untyped `dict` (Python) — use proper types
- MUST NOT: copy-paste code — extract shared logic or import existing utilities
- MUST NOT: hallucinate APIs, endpoints, or library methods — verify they exist first

### Test Quality Gates

- Tests must assert **behavior**, not just exercise code paths — every test needs at least one meaningful assertion on output or side effects
- Test descriptions must describe the expected behavior, not the implementation (`"returns 404 when hotel not found"` not `"calls findOne and throws"`)
- E2E/integration tests must verify the actual **external contract** of the system under test:
  - API services: HTTP status codes, response shapes, error formats
  - CDK/Infra: `cdk synth` succeeds, snapshot matches, resources are correct
  - Frontend: user-visible behavior via browser automation
  - Data pipeline: messages are routed/transformed correctly
- Do NOT write tests that mock so heavily they only test the mocks
- **If the target repo has no test infrastructure:** note this in the Acceptance Criteria and discuss with the user whether to add it or skip test requirements for this story

## Edge Cases

What happens when things go wrong.

- [hallucinate]: stop immediately, revert the hallucinated code, re-read the actual codebase, and resume from the last known-good state
- [test failures]: fix root cause — never skip, disable, or mark tests as `.skip`/`xit`/`@Disabled`
- [ambiguous requirement]: stop and ask the user before assuming — do NOT guess
- [touching shared DB tables]: check which other services use the table (see CLAUDE.md Shared Database section) and verify no other service breaks
- [lint/type errors]: fix before completing — never suppress with `@ts-ignore`, `eslint-disable`, `@SuppressWarnings`, or `# type: ignore`
- [duplicate code detected]: stop, find the existing implementation, and reuse it instead
- [pattern mismatch]: if your code looks different from neighboring files in the same repo, you're doing it wrong — align before continuing
- [tests pass but behavior is wrong]: do not trust green tests alone — verify the feature works as described in the acceptance criteria
- [approach isn't working]: stop, report, propose alternative, wait for approval — do NOT silently pivot or force it
- [change plan diverges]: if you need to create/modify files not listed in the Change Plan, stop and ask before proceeding
- [multi-repo desync]: if one repo's changes are merged but the dependent repo isn't ready, do NOT leave the system in a broken intermediate state — coordinate or feature-flag
- [repo has no test infrastructure]: report this to the user and ask whether to (a) add test infrastructure as part of this story, (b) skip test requirements and note the gap, or (c) write tests that can be enabled later
